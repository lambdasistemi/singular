# Boundary data contracts

- surface-identity-qualified-model-declaration-definition-digest Surface identity: qualified model declaration, definition digest, model
  revision and protocol version. A scenario names only declared operations.
- scenario-stable-corpus-identity-theorem-statement-bindings Scenario: stable corpus identity, theorem/statement bindings, quantified
  inputs, state/action/parameters and setup trace where reachability is required.
  Witness and mutant relationships are explicit. Unsupported or unreachable
  concrete setups are classified; they never become a fabricated successful run.
- driver-result-accepted-transition-declared-boundary-observations Driver result: accepted transition and declared boundary observations, or
  domain refusal with reason. Parse/unsupported-operation/process errors are
  distinct execution failures. No partially decoded success is admitted.
- concrete-observation-actual-operation-outcome-observable-fields Concrete observation: actual operation outcome and all observable fields
  named by the constitutional translation. Input provenance and missing fields
  remain explicit; missing values cannot be replaced by model expectations.
- context-identity-state-externally-supplied-runtime-resources Context/identity state: externally supplied runtime resources with typed
  concrete-to-abstract identity maps persistent across the scenario trace.
  Allocation is allowed only during setup/action; observation is lookup-only.
- execution-receipt-candidate-tree-model-corpus-identities Execution receipt: candidate/tree and model/corpus identities, scenario
  and theorem bindings, actual and expected observations, comparison outcome,
  controls applied, execution command and provenance. Rendered status derives
  from receipts. Historical receipts are immutable evidence, not current passes.

Ordering, quantities, datum shapes, signers/refunds, concrete funding/change and
root realization must be defined in defines-concrete-law-observation-mappings-identities-unobservable before observes-real-system-translates-boundary-types-under excludes or normalizes them.
Proof-only fields remain visible limitations and do not satisfy project-theorem-has-executable-consumers-or-named by fiat.
