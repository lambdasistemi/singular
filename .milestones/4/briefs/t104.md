## Outcome

Anyone acting as a folder can drain every pending request of a registry without knowing in advance how many fit in one transaction: the tool builds a batch, evaluates it, and on refusal splits it, until the queue is empty or a request is individually unfoldable and reported as such.

## Why

The registry has no owner; folding is permissionless, so a folder must be a tool, not a person. Today `TxBuilder.Update` folds the list it is given in one transaction and evaluates execution units; nothing loops, nothing sizes batches, nothing recovers from a size or unit refusal. The limit cannot be a fixed number: it depends on proof sizes, datum sizes and script budgets, which vary with the values and the trie shape. So the "measure the batch limit" story of #71 is replaced by this tool, and #71 is closed: the lookup rows are subsumed by the supply invariant (the representative NFT is the proof of an active key), and the environment record is written by the preprod close.

## The diff

1. `fold-all` (a runner or a library function used by the runners): read the pending request UTxOs at the request address, order them, and fold in batches.
2. Batch sizing by trial: start with all; build and evaluate through the node's evaluation API; on a size or execution-unit refusal, halve; on success, submit, confirm, and continue from the next request with the last successful size as the new starting point. A single request that fails on its own is reported with the node's reason and skipped, never retried in a loop.
3. Proofs are recomputed per batch against the root read back after each confirmation (the discipline `li01` already follows); no proof is reused across batches.
4. A test on a devnet: enqueue N requests with varied value sizes such that they cannot fit one transaction; `fold-all` drains them in more than one batch; the final root equals the mirror's; one poisoned request is reported and skipped.
5. Narrate each batch: size tried, outcome, transaction id.
