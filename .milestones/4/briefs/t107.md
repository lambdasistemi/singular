## Outcome

A writer on any machine can rebuild the registry's trie from the chain alone and then fold against the current root, so attaching to a deployment needs the manifest and a node socket, nothing copied out of band.

## Why

A fold proves a key against the registry's current root, and building that proof needs the whole trie. #106 (M1) carries the trie as `preprod.mirror.json` beside the manifest, with `attach` refusing when the mirror root differs from the chain root. That is safe and enough for one machine. It means a second machine cannot fold without a copy of the file. Readers are unaffected: proving a key is alive needs only the representative NFT.

## The diff

1. `deployment follow`: starting from the bootstrap transaction recorded in the manifest, follow the registry token's spending chain through the node's chain-sync (the `chain-follower` dependency is already pinned; no external indexer or service). Each spend of the state output is a fold; read the consumed request datums (key, value, operation) and the fold's actions, replay them into a fresh trie, and stop at the tip.
2. Verify at the end that the rebuilt root equals the root in the state output at the tip; write `preprod.mirror.json` only on equality, refusing by name otherwise.
3. `attach` gains `--rebuild`: when no mirror file exists, or its root mismatches, run `follow` first.
4. Incremental: a mirror file records the last replayed point; `follow` resumes from it.
5. Test on a devnet: fold several requests from machine A's mirror, delete the mirror, `follow` from the bootstrap, assert the rebuilt root equals the chain root and a subsequent fold is accepted.
